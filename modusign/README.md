# 모두싸인 콘솔 설정 — 서식 8종

콘솔에서 무엇을 어떻게 설정했는지의 기록이다. **계획이 아니라 실측값**이다 —
아래 역할·참여자·순서는 템플릿 상세 조회 API로 읽은 값이고(2026-08-01),
`src/lib/signer/template-labels.ts`의 표와 대조까지 마쳤다.

확인 방법:

```bash
node scripts/verify-templates.mjs   # 조회만 한다. 서명 요청을 보내지 않는다
```

## 서식별 설정

| # | 서식 | 요청 종류 | 서명자 | 역할 입력값 | 서명 순서 |
|---|---|---|---|---|---|
| ① | 기부약정서 `DONATION_PLEDGE` | 계약 서명 요청 | 1명 | `기부자` | — |
| ② | 정기후원약정서 `RECURRING_CONSENT` | 계약 서명 요청 | 1명 | `후원자` | — |
| ③ | 개인정보동의서 `PRIVACY_CONSENT` | 계약 서명 요청 | 1명 | `정보주체` | — |
| ④ | 유산기부약정서 `LEGACY_GIFT` | 계약 서명 요청 | 1명 | `기부자` | — |
| ⑤ | 문화유산후원약정서 `HERITAGE_PLEDGE` | 계약 서명 요청 | 1명 | `후원자` | — |
| ⑥ | 의사확인서 `ATTESTATION` | 계약 서명 요청 | 1명 | `본인` | — |
| **⑦** | **가족인지확인서 `FAMILY_ACK`** | 계약 서명 요청 | **2명** | 1번 `본인` → 2번 `가족` | **순서대로 한 명씩** |
| ⑧ | 보관집행협조약정서 `CUSTODIAN` | 계약 서명 요청 | 1명 | `지킴이` | — |

**역할 입력값이 곧 API 값이다.** `participantMappings[].role`에 그대로 들어가고,
콘솔 문자열과 한 글자라도 다르면 요청이 거부된다. 코드 쪽 표는
`src/lib/signer/template-labels.ts`의 `TEMPLATE_ROLES`이며 위와 일치한다.

⑦만 순서가 실제로 뜻을 갖는다 — **본인이 먼저 서명해야 가족이 인지할 대상이 생긴다**
(서식 제5조). 순서가 뒤집히면 "본인이 서명하지 않은 변경을 가족이 먼저 아는" 상태가 되고,
그건 코드가 409 `SELF_SIGN_REQUIRED`로 막는 바로 그 경우다.

## 하지 않은 것

**"미리 정보 입력하기"를 쓰지 않았다.** 이름·연락처를 템플릿에 넣으면 그 사람에게만
가는 템플릿이 된다. 우리는 API로 매번 다른 사람에게 보내므로 **역할만** 채운다.

**기관 날인란을 참여자로 잡지 않았다.** 서식 본문이 "기관은 기명날인을 하여"라고
정하고 있어 그 도장은 **문서에 인쇄되는 부분**이지 전자서명 참여자가 아니다.
참여자로 잡으면 서명자가 2명이 되어 서명 요청이 두 곳으로 가고 문서가 완료되지 않는다.

그 결과 ①②④⑤⑧에는 우리가 채우지 않는 칸이 2개씩 남는다. API로 확인한 결과
**전부 같은 역할 안의 칸**이라 서명자 수가 늘지 않는다 — 그대로 두는 것이 맞다.
③⑥⑦에 초과가 없는 것도 구조적으로 설명된다: 상대 당사자가 없는 단독 문서라
애초에 기관 날인란이 없다.

## 권장 잠금 설정

```
서명자 설정   ☑ 서명 순서        ☑ 서명자 카드 수
입력 설정     ☑ 문서·입력란      ☑ 요청할 첨부파일
기타 설정     □ 첨부파일         ☑ 외부 참조자
              □ 인증 수단
```

**문서·입력란 고정이 가장 중요하다.** 잠기면 라벨 위치·구성이 바뀌지 않아
우리가 보내는 `dataLabel`이 항상 같은 칸에 꽂힌다.

**인증 수단은 열어 둔다.** 시연에 휴대전화 인증이 붙으면 흐름이 길어지고,
필요해지면 API에서 켤 수 있어야 한다.

⚠ 잠금은 "실수로 바뀌는 것"을 막지, 콘솔에서 의도적으로 재생성하는 것까지 막지 않는다.
템플릿을 다시 만들면 `dataLabel`이 새로 생성되고 **그때 증상은 에러가 아니라 빈칸**이다.
그래서 배포·왕복 전에 `verify-templates.mjs`를 돌린다.

## 구조 — 요청자 입력 / 서명자 입력

8종 전부 이 형태로 맞췄다.

| 칸 | 누가 채우나 | 콘솔 설정 |
|---|---|---|
| 성명·금액·기관명 등 데이터 | **우리 서버** | 요청자 입력 (문서 편집) |
| 말미 성명 · 서명 | 서명자 | 서명자 지정 |

처음에는 모든 칸이 서명자 입력이었다. 그러면 **대화로 정리한 내용을 사용자가
서명 화면에서 다시 타이핑**하게 되어, 이 서비스의 전제가 무너진다.

⚠ 입력란을 옮기면 `dataLabel`이 **새로 생성된다.** 8종을 옮기면서 라벨 41개가
한 번에 갈렸다. 그래서 표는 손으로 고치지 않고 API 덤프에서 생성한다:

```bash
node scripts/verify-templates.mjs --dump   # 실측 라벨을 문서 위치 순으로 출력
```

### 🔴 ⑦에 남은 수정 하나

가족 서명란이 **본인 참여자에 배정**돼 있어 가족의 필드가 0개다.
이대로 요청하면 본인이 가족 서명란까지 서명하게 되고, 그 순간
"가족이 알고 있다"는 기록이 **본인이 대신 그린 서명**이 된다 — FR-554가
방어하려던 것이 정면으로 무너진다. 2순위 가족에게 넘어가도 할 일이 없어
문서가 `ON_GOING`에 머물 수도 있다.

**고치는 법**: `2 입력` 단계에서 아래 두 칸을 선택하고 오른쪽 패널의 서명자를
"가족"으로 바꾼다.

|---|---|
| 가족 성명 | `10601941` |
| 가족 서명 | `9172039f` |

## 왕복 순서

```
1. MODUSIGN_MODE=real 로 전환 (사람이 한다)
2. 서명 요청 1건 → 서명 화면 열기
3. 【서명 전】 필드 인쇄 확인
   · 값이 제 칸에 들어갔는가
   · "100,000원원" 같은 단위 중복이 없는가
   · 기관 칸이 비어 있는가 (정상)
4. 이상하면 서명하지 말고 취소 — 잘못된 문서로 완료까지 가면 2건을 쓴다
5. 정상이면 서명 → 서버 로그에서 첫 웹훅 원문 확인
6. 증빙·해시 생성까지 확인
7. MODUSIGN_MODE=mock 으로 즉시 복귀
```

서명 요청은 잔여가 정해져 있다. 조회(`GET /templates/{id}`)는 소모하지 않으므로
확인은 조회로 먼저 한다 — 실제로 인증 방식·DocType 매핑·⑦ 배정 문제를
서명 0건으로 잡았다.
