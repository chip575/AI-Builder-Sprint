## Q&A 예상 문답 (T808)

| 질문 | 답 |
| ---| --- |
| 유언장을 전자서명 못 하면 모두싸인을 왜 쓰나? | 유언 본문만 안 된다. 유산기부 약정·정기후원·개인정보 동의·Custodian 협조 약정은 전부 유효하다. 어디에 써야 하고 어디엔 쓰면 안 되는지를 아는 것이 CLM의 핵심이다 |
| AI가 유언 내용을 잘못 쓰면? | AI는 초안만 쓰고 사용자가 손으로 옮겨 적는다. 필사 과정 자체가 최종 검증 단계다 |
| 법률 자문 아닌가? | 모든 화면에 고지. 계산은 법령 상수 테이블 기반이고 LLM은 수치를 생성하지 않는다 (ADR-3) |
| 개인정보는? | 주민번호·계좌번호 원문 미저장, 마스킹만. RLS로 DB 레벨 격리 |
| 실제로 쓸 수 있나? | 부산 지자체 시드로 실제 흐름 재현. 결제만 기존 채널에 연결하면 운영 가능 |
| 세액공제율이 바뀌면? | 상수 파일 한 곳. `verifiedAt` 필드로 갱신 시점 추적 |
| 왜 AI가 아니라 사람이 결정하게 하나? | 기부액과 수증자는 삶의 결정이다. AI가 제안하는 순간 그건 그 사람의 뜻이 아니게 된다 |

## 스펙 드리프트 방지 (SDD의 실패 원인 1위)

Spec Kit·Kiro류 도구의 가장 흔한 실패는 **스펙을 세션 시작용 문서로만 쓰고 코드 생성이 시작되면 다시 코드가 진실의 원천이 되는 것**이다. 방지책:

1. **커밋 메시지에 FR ID를 넣는다.** `feat(FR-201): 거주 지자체 기부 차단`
2. 스펙과 다르게 구현하고 싶으면 **코드보다 이 문서를 먼저 고친다.**
3. 각 Phase 종료 게이트에서 해당 FR의 수락 기준을 **실제로 실행해 확인**한다. 눈으로 읽고 넘어가지 않는다.
4. 시간이 없어 못 한 FR은 삭제하지 말고 `DEFERRED`로 표시 — 발표에서 "의도적으로 남긴 것"과 "못 한 것"을 구분해 말할 수 있어야 한다.
