# 남기다 (NAMGIDA)

> **한 줄 정의** — 인생의 마지막 정리를 대화로 돕고, 그 이야기를 살아있는 유서(마음 유언)로 저장·관리하며, 대화에서 갈라져 나오는 기부·유산·자산 서류를 **법이 인정하는 방식으로만** 체결·보관·이행하는 서비스.

## 1\. 왜 두 주제가 하나로 묶이는가

|  | 요구 |
| ---| --- |
| 모두싸인 과제② | "마음을 남기는 서명" — 기부·봉사·유산기부 약정의 증빙·이행 관리 |
| 공통 주제 | AI가 사람을 대체하지 않고 더 인간답게 만드는 도구 |

**교집합:** 사람이 가장 인간다운 순간 — 무언가를 남기기로 결심하는 순간 — 은 절차의 마찰 때문에 대부분 실행되지 않는다. AI가 그 마찰(질문 설계·서류화·법적 검증)을 제거하고, 모두싸인이 그 결심을 되돌릴 수 없는 증빙으로 만든다.

AI는 **결심을 대신 하지 않는다. 결심을 가능하게 한다.** 이것이 우리의 "인간다움" 정의다.

## 2\. 5대 원칙 (위반 시 해당 설계는 기각)

**P1. AI는 묻고, 사람이 정한다.** AI가 기부 금액·수증자·유언 내용을 제안하거나 결정하지 않는다. AI의 역할은 질문 / 정리 / 초안 / 검증뿐. 모든 확정은 사용자의 명시적 승인(diff 확인 후 클릭)을 거친다.

**P2. 법적 유효성 게이트를 통과하지 않은 문서는 생성하지 않는다.** 전자서명이 법적으로 무효인 문서 유형에 전자서명을 붙이지 않는다. 무효 유형은 유효한 대체 경로로 라우팅한다.

**P3. 모든 주장에는 근거가 붙는다.** 세액공제 계산·기부 한도·유언 요건 등 모든 법적 안내는 법령 조문 ID와 갱신일자를 UI에 함께 노출한다. LLM이 법률 수치를 생성하지 않는다 — 수치는 코드화된 룰 테이블에서만 나온다.

**P4. 거절 가능성을 항상 열어둔다.** 어떤 단계에서도 중단·삭제·철회 가능. "나중에 생각할래요" 버튼은 모든 화면에 존재한다. 다크패턴·긴급성 조성 금지. 유언·상속 주제 특성상 사용자가 감정적으로 취약할 수 있음을 전제한다.

**P5. 증빙은 서명 이후에도 살아있다.** 체결은 끝이 아니라 시작. 정기후원 갱신·유언 재검토 알림·집행 시점 전달까지 추적한다. (= CLM 생애주기 커버리지 12점 직결)

## 3\. 구조 — 중심 축과 가지 (마음 유언 모델 · 2026-07-28 개정)

### 3.0 왜 바꿨는가

이전 구조는 트랙 A/B/C를 **먼저 고르고** 대화를 시작했다. 이것은 §1과 충돌한다 — 결심이 죽는 이유가 절차의 마찰이라면서, 문 앞에서 "당신은 기부인가 유언인가 정리인가"라는 분류를 요구하는 것 자체가 마찰이다. 사람은 "정리를 좀 하고 싶다"고 오지, 자기가 어느 트랙인지 모른다.

### 3.1 중심 축 — 마음 유언

서비스의 등뼈는 하나다. **존엄요법 질문 프로토콜에서 착안한 회상 인터뷰**로 인생의 마지막 정리를 돕는 대화.

*   존엄요법이 1~2회로 압축된 것은 인력 제약 때문이었다. 마음 유언은 그 압축을 풀되, **"장기 서비스"가 아니라 "기간 무관 관리"다.** 세션 간격이 10분이든 6개월이든 시스템 동작은 같고, 간격이 아무리 벌어져도 저장·관리·재개가 유지된다. **세션의 주기가 긴 것이지, 서비스가 장기인 것이 아니다.** 짧게 써도 완전하고, 길게 써도 관리된다.
*   세션마다 수집된 이야기는 **문서화되어 저장·관리**되고, **살아있는 유서(마음 유언)** 로 계속 정리된다. 완성 시점이 따로 없다 — 갱신되는 과정 자체가 산출물이다.
*   뜻이 바뀌면 **의사 이력(FR-550)** 에 노드가 쌓인다.
*   마음 유언 자체는 `NON_BINDING` — 법적 효력이 없음을 명시하고 보관·전달한다. 법적 효력이 필요한 부분은 가지로 분리된다.
*   표현 주의: **"AI가 존엄요법을 제공한다"고 말하지 않는다.** 질문 프로토콜에서 착안한 **기록 도구**다. (윤리 방어선)

### 3.2 가지 — 법적 서류는 대화에서 갈라져 나온다

사용자는 "기부 약정을 하겠다"고 앉지 않는다. 자기 삶을 이야기한다. 그 대화에서 서명 가능한 문서가 갈라져 나온다.

| 대화 신호 (예) | 가지 (branch) | 게이트 | 산출물 |
| ---| ---| ---| --- |
| "그 재단에 지금 좀 보태고 싶다" | `DONATION_NOW` 기부 | ESIGN\_OK | 기부약정서 + 동의서 (FR-200) |
| "문화유산 지키는 데 쓰였으면" | `HERITAGE_SUPPORT` 문화유산 후원 | ESIGN\_OK | 후원 약정서 (FR-205) |
| "내가 떠나면 일부는 그곳에" | `LEGACY_GIFT` 유산기부 (사후) | ESIGN\_OK | 사인증여 약정 + 유류분 고지 (FR-304) |
| "유언장을 남겨야겠다" | `HANDWRITTEN_WILL` 자필유언 | ESIGN\_INVALID | 필사 가이드 (FR-302) |
| "뭐가 어디 있는지 정리부터" | `ESTATE` 자산정리 | 혼합 | 인벤토리 + Custodian 약정 (FR-400) |

**가지 규칙 (P1의 확장)** — 상세는 01.6 FR-115. 명시적 의사는 **직접 진입(Express)** 으로 축을 건너뛴다.

1. AI는 가지를 열지 않는다. **제안만 한다.** 확정은 사용자가 한다.
2. 근거 발화 없는 제안은 폐기된다.
3. 사용자가 닫은 가지는 다시 제안하지 않는다.
4. 무거운 가지(유산기부·자필유언)의 AI 감지 제안은 **다음 세션에 재확인**을 거친다 — 감정적 순간의 즉흥 결정을 시스템이 막는다. (본인이 직접 진입한 경우는 숙려 화면으로 대체)

### 3.3 동일 파이프라인

진입만 바뀌었다. 1단계(대화)가 중심 축의 세션이 되고, 가지가 열릴 때마다 2~6단계가 그 가지에 대해 실행된다.

```markdown
1. 대화        마음 유언 세션        Solar LLM (회상 인터뷰 · 세션 주기 무관)
2. 구조화      Extraction           Solar structured output (가지별 스키마)
3. 검증        Validity Gate        룰 엔진 (법령 테이블)   <-- 핵심 자산
4. 문서화      Draft                템플릿 엔진 + Solar (문체만 담당)
5. 체결        Execute              모두싸인 API | 자필증서 가이드
6. 보관·이행   Custody & Lifecycle  Webhook + 리컨실러 + 스케줄러
```

모든 가지는 2~6단계 코드를 공유한다. **가지 추가 비용 ≈ 템플릿 1개.** 이것이 해커톤 기간 내 구현이 가능한 이유이자, 심사에서 "확장 가능한 구조"로 설명할 근거다.

# 00.1 · 법적 유효성 게이트 & 법령 룰 테이블

## 4\. 핵심 차별점 — 법적 유효성 게이트

경쟁팀이 거의 확실히 놓칠 지점이다. **"AI 유언장을 만들어 전자서명한다"는 아이디어는 법적으로 무효다.** 우리는 이 사실을 숨기지 않고 제품의 중심에 놓는다.

| 문서 유형 | 전자서명 효력 | 근거 | 우리 처리 |
| ---| ---| ---| --- |
| 기부 약정서 | 유효 | 계약 | 모두싸인 체결 |
| 정기후원 동의 | 유효 | 계약 | 모두싸인 체결 |
| 개인정보·세액공제 동의 | 유효 | 개인정보보호법 제22조 | 모두싸인 체결 |
| 자원봉사 약정 | 유효 | 계약 | 모두싸인 체결 |
| 유산기부 약정(사인증여) | 유효 | 민법 제562조 | 모두싸인 체결 + 유류분 경고 |
| 유언장 | 무효 | 민법 제1060·1065·1066조 | 자필 필사 가이드 + 공증 안내로 라우팅 |
| 마음의 편지(윤리적 유언장) | 효력 없음(의도적) | — | 서명 없이 보관, 지정 시점 전달 |

### 법적 근거 (UI·발표 슬라이드에 그대로 노출)

*   **민법 제1060조** — 유언은 본법에 정한 방식에 의하지 아니하면 효력이 생기지 아니한다.
*   **민법 제1065조** — 유언 방식은 자필증서·녹음·공정증서·비밀증서·구수증서의 5종.
*   **민법 제1066조 제1항** — 자필증서 유언은 전문·연월일·주소·성명을 **자서**하고 **날인**하여야 한다.
*   **대법원 2006. 9. 8. 선고 2006다25103, 25110** — 날인 없는 유언장은 자필증서 유언으로서 무효.
*   **대법원 2014. 10. 6. 선고** — 주소를 자서하지 않으면 무효. 유언자 특정에 지장이 없어도 마찬가지.
*   대법원은 **법이 특별히 서면 형식을 요구하는 경우 전자문서가 그 요건을 충족한다고 볼 수 없다**고 판시.

**→ 그래서 우리는 유언을 전자서명하지 않고, AI가 자필 필사를 실수 없이 하도록 돕는다.**
자필증서 유언의 3대 무효 원인(**주소 미자서 · 날인 누락 · 연월일 불특정**)을 체크리스트로 차단하는 것이 트랙 B의 실질 가치다. 이건 "AI가 결과 품질에 기여" 항목의 직접 증거가 된다.

### 게이트 판정 결과 3종

| 결과 | 의미 | 후속 |
| ---| ---| --- |
| `ESIGN_OK` | 전자서명으로 효력 발생 | 모두싸인 서명 요청 |
| `ESIGN_INVALID` | 전자서명해도 무효 | 대체 경로(자필/공증) 안내 + 사유·조문 표시 |
| `NON_BINDING` | 법적 구속력 없음이 의도된 문서 | 서명 없이 보관, 안내 문구 필수 |

## 5\. 고향사랑기부제 룰 테이블 (하드코딩 · LLM 생성 금지)

| 항목 | 값 | 비고 |
| ---| ---| --- |
| 연간 기부 상한 | 2,000만원 | 2025.1.1~ 상향 (기존 500만원) |
| 기부 불가 대상 | 주민등록상 거주 광역·기초 지자체 | 고향사랑기부금법 제4조 |
| 답례품 | 기부금의 30% 이내 | 현금·귀금속·유가증권 제외 |
| 세액공제 ~10만원 | 전액 (100%) |  |
| 세액공제 10만~20만원 | 44% |  |
| 세액공제 20만원 초과 | 16.5% | 특별재난지역 33% |

**검산 예시 (그대로 유닛테스트로 사용)**
*   100만원 기부 → 10만 + 4.4만 + (80만 × 16.5% = 13.2만) = **27.6만원**
*   특별재난지역 100만원 → 10만 + 4.4만 + (80만 × 33% = 26.4만) = **40.8만원**
*   10만원 기부 → 공제 10만원 + 답례품 3만원 = 체감 13만원

> 세액공제는 기부자 본인에 한하고 이월공제가 없으며, 개인의 결정세액에 따라 실제 공제액이 달라진다.  
> → UI에서 **"예상 공제액"** 으로만 표기하고 확정 표현 금지. 결정세액 관련 주석 필수.

### 룰 테이블 관리 규칙

## 7\. 용어 정의 (코드·문서 전체에서 이 표기만 사용)

| 용어 | 의미 |
| ---| --- |
| Spine (중심 축) | 마음 유언을 만드는 장기 회상 인터뷰 과정. intents.kind = SPINE\_SESSION |
| Branch (가지) | 축의 대화에서 갈라져 나오는 법적 서류 흐름. intents.kind = BRANCH + branch\_type |
| HeartWill (마음 유언) | 축의 산출물. 살아있는 유서. NON\_BINDING — 법적 효력 없음 명시, 완성 시점 없음, 버전으로 관리 |
| Intent | 사용자의 정리되지 않은 의향. 세션 1건 = Intent 1건 |
| IntentFact | IE로 추출된 구조화 항목. key, value, confidence, sourceSpan |
| Validity Gate | 문서 유형별 전자서명 효력 판정 룰 엔진 |
| DocumentDraft | 게이트 통과 후 생성된 문서 초안. 아직 서명 전 |
| SignatureRequest | 모두싸인 문서 1건에 대응. modusignDocumentId 보유 |
| Evidence | 완료 PDF + 서명 이력 + 해시 + 타임스탬프 |
| Obligation | 체결 이후 이행 의무 (정기후원 회차, 유언 재검토, 이어쓰기 초대) |
| Custodian | 서비스 내 역할. 인벤토리·유언 위치를 열람하고 집행에 협조하기로 약정한 지정인. 열람권은 카테고리 단위 (NFR-713) |

### 7.1 Custodian은 유언집행자가 아니다

| 구분 | Custodian | 유언집행자 |
| ---| ---| --- |
| 근거 | 우리 서비스의 약정 (계약) | 민법상 지위 |
| 권한 발생 | 협조 약정 서명 완료 시 | 상속 개시 후 |
| 할 수 있는 것 | 인벤토리 열람(허용 범위 내), 유언장 위치 확인, 집행 협조 | 유언 내용의 법적 집행 |
| 법적 집행 권한 | 없음 | 있음 |

**표기 규칙**: 코드·문서·UI 어디에서도 Custodian을 유언집행자로 번역·표기하지 않는다. 사용자 화면 표기는 "지킴이" 또는 "보관 협조자". 협조 약정서 본문에 "본 약정은 민법상 유언집행자 지정이 아닙니다" 고지를 포함한다.

### 7.2 유산기부(LegacyGift)와 문화유산 후원(HeritageSupport)은 다르다

한자는 둘 다 유산(遺産)이지만 개념이 다르다. **코드에서 절대 혼용하지 않는다.**

| 구분 | LegacyGift 유산기부 | HeritageSupport 문화유산 후원 |
| ---| ---| --- |
| 의미 | 사망 후 남기는 재산 (legacy) | 세대를 잇는 문화적 자산 (heritage) |
| 시점 | 사후 효력 (사인증여, 민법 562조) | 생전 후원 |
| branch\_type | LEGACY\_GIFT | HERITAGE\_SUPPORT |
| doc\_type | LEGACY\_GIFT\_AGREEMENT | HERITAGE\_SUPPORT\_PLEDGE |
| 템플릿 env | MODUSIGN\_TEMPLATE\_LEGACY\_GIFT | MODUSIGN\_TEMPLATE\_HERITAGE\_PLEDGE |
| 필수 고지 | 유류분 침해 가능성 + 전문가 상담 안내 | 없음 (익명 옵션만) |
| 절차 | 무거운 가지 — 제안 후 다음 세션 재확인 필수 (FR-115) | 가벼운 가지 — 즉시 진행 가능 |
| 근거 FR | FR-304 | FR-205 |

**교차 케이스**: 문화유산 단체에 사후 재산을 남기는 경우 = 수혜자가 heritage 단체인 LEGACY\_GIFT다. 이때도 문서·절차는 유산기부 쪽(유류분 고지, 다음 세션 재확인)을 따른다. **수혜자의 성격이 절차를 바꾸지 않는다.**

### 7.3 폐기 용어

Track (DONATION / WILL / ESTATE) 은 **폐기**한다. kind (SPINE\_SESSION 또는 BRANCH) + branch\_type (DONATION\_NOW / HERITAGE\_SUPPORT / LEGACY\_GIFT / HANDWRITTEN\_WILL / ESTATE) 로 대체한다.

## 0\. 대상 — 누구에게, 왜, 어떻게, 무엇을 (2026-07-28 v2)

> **한 문장** — 죽음이 구체화되는 사건을 겪었지만 아직 시간이 있는 사람에게, 남기려는 결심이 절차의 마찰과 기록되지 않는 변심으로 사라지지 않도록, 대화로 정리하고 **법이 인정하는 방식으로만** 서명하며 세션 주기와 무관하게 저장·관리·갱신함으로써 — **마음은 살아있는 유서로, 실행은 유효한 약정으로** 남기게 한다.

| 축 | 내용 |
| ---| --- |
| 누구에게 | 사별·진단·은퇴·칠순 등 죽음이 구체화되는 사건을 겪고, 시간과 판단력이 온전한 사람. 대표 형상 = P2 |
| 왜 | 결심은 의지 부족이 아니라 절차의 마찰로 사라지고, 뜻의 변화는 기록되지 않아 분쟁이 되기 때문 |
| 어떻게 | 존엄요법 착안 대화로 묻고 → 게이트로 효력을 검증하고 → 세션 주기 무관하게 저장·관리·갱신 (이미 결심한 사람은 대화를 건너뛰고 실행부터 — Express) |
| 무엇을 | 마음 = 살아있는 유서(마음 유언, NON\_BINDING) / 실행 = 기부·유산·자산 약정(ESIGN\_OK) + 자필유언 필사 가이드 |

**적용 범위 주석** — 사건 기반 정의는 **축(마음 유언) 사용자의 조건**이다. P3처럼 가지만 쓰는 사용자는 이 정의 밖에서도 정상 수용된다 (기간 무관·세션 1회 프레임). 즉 정의는 "누가 축을 시작하는가"를 좁히는 것이지, 서비스 이용 자격을 좁히는 것이 아니다.

### 1차 타겟 (데모·구현 기준 · 점검 v2)

| # | 페르소나 | 사건 = 진입 트리거 | 주 경로 | 검증 근거 |
| ---| ---| ---| ---| --- |
| P1 | 사별을 겪은 자녀 (40~50대) | 부모상 이후 "나는 미리 해야겠다" — 본인의 축을 일찍 시작하는 사용자 | 축 시작 (자산·디지털 유산 비중 높음) | StoryWorth — 사별이 구매 트리거 |
| P2 | 정리를 시작한 시니어 (60~70대) — 대표 형상 | 칠순·은퇴·건강 이상 신호 | 축 → 가지 → 생애주기 전부 경험 | 유언대용신탁 수요의 전 단계 |
| P3 | 고향 기부자 (40~50대) — 가지 단독 사용자 | 고향사랑기부 관심, 이미 결심 (사건 정의 밖 — 위 주석) | 직접 진입(Express) → DONATION\_NOW | 고향사랑e음·busanlove 이용자 |
| P4 | 기부처·단체 담당자 (기관, 도입 주체) | 약정·증빙 관리 업무 | 대시보드 (FR-600) | FreeWill의 비영리 B2B 모델 |

**P1 재정의 (점검 결과)** — 기존 "개시자(부모 초대)" 역할은 초대 흐름 미결정 상태에서 페르소나의 근거가 될 수 없다. P1의 검증된 실체는 **사별 후 자기 정리를 일찍 시작하는 본인 사용자**다. "자녀→부모 초대"(StoryWorth 구매자≠사용자)는 P1의 **확산 방향**으로 격하하며, 기능 채택 여부는 페르소나 태스크의 결정 항목으로 유지한다.

**이차 행위자 (페르소나 아님)** — 가족(인지 서명·열람 수신인), Custodian(협조 약정·부분 열람), 유족(사후 열람·검증). 이들은 타겟이 아니라 **시스템 행위자**다 — 스스로 서비스를 시작하지 않고 P1~P3의 행위로 등장한다. 화면·문안은 필요하지만 획득 전략의 대상이 아니다.

### 호스피스 환자는 왜 대표 형상이 아닌가 (데이터 재확인)

기간 무관 관리 프레임에서는 짧은 주기 사용자도 자연 수용되므로, 배제 논리를 "구조적 모순"에서 **"차별점 수혜 불가 + 리스크 + 비대표성"** 으로 교체한다.

1. **차별점이 작동할 시간이 없다.** 우리 차별점은 시간을 관리하는 것(갱신·재검토·의사 이력)인데, 국내 입원형 호스피스 이용 기간은 평균 **15일** 수준이다. 이들이 받는 가치는 축(회상·기록)에 국한 — 서비스의 부분집합이다. 부분집합의 사용자를 대표로 세우면 서비스가 "기록 도구"로 축소되어 보이고, 모두싸인 35점의 서사(계약 생애주기)가 사라진다.
2. **비대표적이다.** 호스피스 이용은 암 사망자 기준으로도 약 22% 수준의 소수이고 이용 시점도 임종에 임박해 있다. 분포의 극단값이지 중심이 아니며, "아직 시간이 있을 때 미리"라는 우리 주장과도 모순된다.
3. **리스크가 핵심 가치와 충돌한다.** 의사능력·서명 유효성 리스크 최고조("임종 직전 전자서명"은 유류분 분쟁 공격 1순위), 기관·가족 매개 필수 — 스스로 여는 사용자가 아니다.

**그러나 배제가 아니라 위치의 문제다.** ① 문제 기원 서사(존엄요법이 말기 환자에게조차 인력 때문에 닿지 못했다) ② 설계 근거(저부하·세션 분할) ③ **B2B 확산 단계 — 축(기록) 중심 도입 + 서명 가지는 입회·컨디션 요건 강화 버전.** 심사자가 물으면 그때 이 답을 꺼낸다.

## FR-100 · 공통 파이프라인

### FR-101 · 대화형 의향 정리
사용자는 자유 대화로 의향을 표현할 수 있어야 한다. 시스템은 축 질문과 가지별 슬롯을 따라 미확정 항목을 하나씩 좁혀간다.

*   **한 번에 하나의 질문만** 던진다 (인지 부하 최소화, 고령 사용자 고려)
*   시스템은 금액·대상·수증자를 **먼저 제안하지 않는다** (헌법 P1)
*   사용자가 "모르겠다"고 하면 선택지를 제시하되 **선택 안 함**도 항상 포함
*   모든 화면에 **"나중에 생각할래요"** 가 있고, 누르면 현재까지 상태를 저장하고 종료

**수락 기준**
*   Given 사용자가 "부산에 기부하고 싶어요"만 입력했을 때, When 대화를 시작하면, Then 시스템은 금액을 먼저 묻지 않고 **어떤 분야에 쓰이길 원하는지**부터 묻는다.
*   Given 대화 중 아무 시점에, When "나중에 생각할래요"를 누르면, Then 진행 상태가 저장되고 재접속 시 그 지점부터 이어진다.

> **『맥락』** 결심은 의지가 없어서 사라지는 게 아니라 절차의 마찰 때문에 사라진다. 폼을 대화로 바꾸는 것이 이 서비스의 출발점이다. "금액을 먼저 묻지 않는다"는 헌법 P1을 대화 설계 층위로 내린 것 — AI가 먼저 숫자를 던지면 사용자는 앵커링되고, "AI가 결정했다"는 지적을 방어할 수 없게 된다.

### FR-102 · 구조화 추출
대화 종료 시 시스템은 가지별 고정 스키마에 따라 항목을 추출해야 한다.

*   각 추출 항목은 **값 + 신뢰도 + 대화 원문 위치**를 함께 보유
*   신뢰도가 임계치 미만이거나 필수 항목이 비면 **추측하지 않고 되묻는다**

**수락 기준**
*   Given 사용자가 금액을 "한 십만원쯤"이라 말했을 때, When 추출하면, Then 값은 100000, 신뢰도는 중간으로 표시되고 **사용자 확인을 요구**한다.
*   Given 필수 항목(기부처)이 비었을 때, When 문서 생성을 시도하면, Then 차단되고 해당 항목을 묻는 화면으로 돌아간다.

> **『맥락』** 스키마 강제가 없으면 LLM은 빈칸을 그럴듯하게 채운다 — 가장 위험한 실패 모드. 신뢰도와 원문 위치를 함께 들고 다니는 이유는 "이렇게 말씀하셨어요"를 화면에 띄우기 위해서다. (구조화 담당은 Solar structured output — 02.5)

### FR-103 · 확인 및 편집
문서 생성 직전, 추출된 모든 항목을 한 화면에서 보여주고 **각 항목을 인라인 편집**할 수 있어야 한다.

**수락 기준**
*   Given 확인 화면에서, When 어떤 항목이든 수정하면, Then 재추출 없이 즉시 반영되고 관련 계산(세액공제 등)이 재계산된다.
*   Given 사용자가 확인 버튼을 누르지 않았을 때, When 문서 생성 API가 호출되면, Then 거부된다.

> **『맥락』** 헌법 P1을 **화면으로 강제하는 유일한 지점.** "확인 없이는 서버가 거부한다"는 검증 가능한 사실이고, 시연하면 "AI가 결정하는 것 아니냐"는 질문이 그 자리에서 끝난다.

### FR-104 · 법적 유효성 게이트
모든 문서 생성 요청은 게이트를 통과해야 한다. 게이트는 `ESIGN_OK` / `ESIGN_INVALID` / `NON_BINDING` 중 하나를 반환한다.

**수락 기준**
*   Given 문서 유형이 유언장일 때, When 서명 요청을 시도하면, Then `ESIGN_INVALID`가 반환되고 **민법 제1060·1066조를 인용한 설명**과 함께 자필 필사 경로로 라우팅된다.
*   Given 게이트 결과가 `ESIGN_INVALID`일 때, When 어떤 경로로든 서명 API를 호출하면, Then 서버가 차단한다 (UI 우회 불가).

> **『맥락』** 프로젝트 전체를 지탱하는 항목. 순수 함수 분리(ADR-2)는 유닛테스트 시연을 위해, LLM 비의존은 환각 차단을 위해. UI가 아니라 **서버에서** 차단한다 — 버튼 숨김은 눈속임이고 API 직접 호출로 드러난다.

## FR-200 · 기부 가지 (DONATION\_NOW · HERITAGE\_SUPPORT)

### FR-201 · 고향사랑기부 흐름
부산 고향사랑기부 흐름을 재현한다: **기부 약정 → 답례품 선택 → 세액공제·개인정보 동의 → 전자서명 증빙**

**수락 기준**
*   Given 사용자의 신고 주소가 부산일 때, When 부산 기부를 선택하면, Then **거주 지자체 기부 불가**를 고향사랑기부금법 제4조와 함께 안내하고 진행을 차단한다.
*   Given 연간 누적 기부액이 2,000만원을 초과하게 될 때, When 금액을 입력하면, Then 상한 초과 경고를 표시한다.
*   주소는 **자기 신고 기반**이다 — 화면에 "실제 기부 시 공식 채널에서 확인됩니다" 고지를 표시한다.

> **『맥락』** 지역사회 가점 5점의 실체. 끝까지 진행했다가 막히는 것이 최악의 경험이므로 **진행을 막는 것 자체가 기능**이다. 시스템은 주민등록 주소를 검증할 수 없으므로 자기 신고임을 명시한다 (Q&A 방어).

### FR-202 · 세액공제 예상액 계산

**수락 기준**
*   Given 100만원 입력, When 계산하면, Then **276,000원**이 표시되고 `10만(전액) + 4.4만(44%) + 13.2만(16.5%)` 산식이 함께 노출된다.
*   Given 특별재난지역 지자체 선택, When 100만원 입력하면, Then **408,000원**이 표시된다.
*   Given 어떤 금액이든, When 결과를 표시하면, Then "예상 금액이며 개인의 결정세액에 따라 달라짐" 고지가 항상 함께 표시된다.

> **『맥락』** 기부 이탈 원인 1순위가 "얼마 돌려받는지 모름". 동시에 **환각 위험이 가장 큰 지점** — 수치는 코드 룰 테이블에만 존재하고 LLM은 `[CALC:]` 토큰만 뱉는다 (ADR-3). 검산 3케이스는 유닛테스트로 고정.

### FR-203 · 답례품 선택

**수락 기준**
*   Given 10만원 기부, When 답례품 목록을 열면, Then 3만원 한도가 표시되고 초과 조합은 선택 불가 상태가 된다.
*   Given 답례품 목록, When 렌더링하면, Then 현금·귀금속·유가증권 항목은 존재하지 않는다.

> **『맥락』** 법정 제약이므로 경고가 아니라 **선택 자체를 막는다.** 금지 품목은 데이터에 존재하지 않게 한다 — 없는 것은 실수로 노출될 수 없다.

### FR-204 · 정기후원 약정

**수락 기준**
*   Given 월 3만원 12회 정기후원, When 약정서를 생성하면, Then 총 36만원·해지 방법·최초 출금일이 문서 본문에 포함된다.
*   Given 정기후원 약정이 체결되면, When 체결 완료 시, Then **갱신 Obligation이 자동 생성**된다 (FR-508 연결).

> **『맥락』** **생애주기 12점의 진입점.** 일시 기부만 있으면 CLM을 보여줄 대상이 없다. 해지 방법 명시는 P4의 문서 층위 적용.

### FR-205 · 문화유산 후원 약정 (HERITAGE\_SUPPORT)

**수락 기준**
*   Given 문화유산 후원 선택, When 약정서를 생성하면, Then 대상 유산명과 후원 용도가 문서에 명시되고, 익명 선택 시 기부자명이 외부 노출 항목에서 제외된다.

> **『맥락』** 과제 원문 명시 요구. 유산기부(LEGACY\_GIFT)와의 구분은 00.2 §7.2 — **수혜자가 아니라 시점이 절차를 정한다.**

### FR-206 · 자원봉사 약정 — 최소 유지 확정

**수락 기준**
*   Given 봉사 약정 체결 완료, When 단체 대시보드를 열면, Then 해당 봉사자가 약정 시간과 함께 목록에 나타난다.

> **『맥락』** 과제 원문 명시 항목이므로 **완전 삭제하지 않는다.** 스키마 + 템플릿 1종만 유지하고 발표에서 "동일 파이프라인" 한 문장으로 처리한다.

# 01.2 · FR — 유언·유산기부 가지 & 자산정리 가지

**이 페이지는** 유언·유산기부 가지(FR-300 — HANDWRITTEN\_WILL·LEGACY\_GIFT)와 자산정리 가지(FR-400 — ESTATE)를 다룬다.
핵심은 **FR-302 자필 필사 가이드** — 유언은 전자서명이 무효이므로, AI가 자필 작성을 실수 없이 하도록 돕는다.
연결된 배점은 창의성 20(FR-302+304) · 인간다움 15(FR-301·303) · AI 통합 10(FR-401).
이 가지들은 감정적으로 무거운 영역이다. **속도가 아니라 안전이 기준이다.**

유언·유산기부: `FR-301 회상(축의 엔진)` → `FR-302 자필 초안` / `FR-303 마음의 편지` / `FR-304 유산기부 약정` **3갈래 분리**
자산정리: `FR-401 업로드 판독` → `FR-402 인벤토리` → `FR-404 수증자 매핑` → `FR-405 Custodian 약정`

## FR-300 · 유언·유산기부 가지 (HANDWRITTEN\_WILL · LEGACY\_GIFT)

> 무거운 가지다. AI 감지 제안은 다음 세션 재확인, 본인 직접 진입은 숙려 화면을 거친다 (FR-115).

### FR-301 · 회상 인터뷰 — 축의 엔진 (01.6 FR-110에서 승격)
재산 목록이 아니라 **삶의 이야기**로 시작하는 질문 세트를 제공한다. 존엄치료 사전돌봄계획 질문지의 구조를 참고하되, 의료 결정은 다루지 않는다.

질문 축 (각 축 3~5문항, 총 20문항 내외):
1. **살아온 이야기** — 가장 잘한 결정, 가장 고마운 사람, 자랑스러운 일
2. **가치** — 돈보다 중요하게 여긴 것, 후대에 이어졌으면 하는 것
3. **관계** — 꼭 전하고 싶은 말이 있는 사람, 아직 못 한 말
4. **남기고 싶은 것** — 물건에 얽힌 이야기, 기부하고 싶은 뜻
5. **당부** — 남은 사람들이 어떻게 지내길 바라는지

**수락 기준**
*   Given 축을 시작할 때, When 첫 질문이 표시되면, Then 그것은 재산·금액에 관한 질문이 **아니다**.
*   Given 어떤 질문에서든, When 사용자가 건너뛰면, Then 재질문하지 않고 다음으로 넘어간다.
*   Given 사용자가 죽음·상실에 대해 감정적 반응을 보이면, When 시스템이 응답하면, Then 다음 질문으로 재촉하지 않고 머무를 수 있는 선택지를 준다.

### FR-302 · 자필증서 유언 초안 & 필사 가이드
정리된 내용으로 자필증서 유언 **초안 텍스트**를 생성하고, 사용자가 손으로 옮겨 적도록 안내한다.

*   초안은 **큰 글씨·고대비**로 표시되고 인쇄 가능
*   4대 필수요건 체크리스트를 **하나씩 순차 확인** (한 번에 전체 체크 불가)
    1. 전문(全文)을 직접 손으로 썼는가
    2. **연월일**을 썼는가 (연·월·일 모두, "○년 ○월 길일" 불가)
    3. **주소**를 직접 썼는가 (인쇄·스티커 불가)
    4. 성명을 쓰고 **날인**했는가 (도장 또는 지장)
*   각 항목 옆에 무효 판례를 근거로 한 1줄 설명
*   완성본을 사진으로 업로드하면 **보관**하고, 사용자가 지정한 Custodian에게 위치를 공유

**수락 기준**
*   Given 유언 초안 화면, When 전자서명 버튼을 찾으면, Then **존재하지 않는다.**
*   Given 체크리스트 4항목 중 하나라도 미확인, When 다음 단계를 시도하면, Then 차단된다.
*   Given 초안이 생성될 때, When 화면을 보면, Then "이 문서는 손으로 옮겨 적어야 효력이 있습니다"가 최상단에 표시되고 민법 제1066조가 인용된다.
*   Given 초안 생성 완료, When 안내를 보면, Then 공정증서 유언(공증) 대안이 장단점과 함께 제시된다.

### FR-303 · 마음의 편지 (윤리적 유언장)
법적 효력이 없음을 명시한 상태로, 가족·지인에게 남기는 글을 작성한다.

*   회상 인터뷰 내용을 재료로 AI가 **초안**을 쓰되, 사용자가 반드시 수정 단계를 거친다
*   AI가 쓴 문장과 사용자가 쓴 문장을 **시각적으로 구분** (헌법 P1)
*   수신인·전달 시점 지정

**수락 기준**
*   Given AI 초안이 생성되면, When 표시되면, Then AI 생성 부분이 색으로 구분되고 "직접 고쳐 쓰세요" 유도가 있다.
*   Given 편지를 저장할 때, When 저장하면, Then "법적 효력이 없는 문서입니다" 고지가 문서 상단에 영구 포함된다.

### FR-304 · 유산기부 약정서 (LEGACY\_GIFT · 전자서명 대상)
유산 일부를 특정 기관에 남기려는 의사는 **유언과 분리해** 사인증여 약정서로 만들고 전자서명한다.

**수락 기준**
*   Given 대화에서 기부 의사가 감지되면, When 문서를 생성하면, Then 유언 초안과 유산기부 약정서가 **별개의 문서 2건**으로 분리 생성된다.
*   Given 유산기부 약정서 생성 시, When 표시되면, Then **유류분 침해 가능성 고지**와 전문가 상담 안내가 포함된다. (금액 계산은 하지 않음)

### FR-305 · 재검토 알림
유언 관련 문서는 체결·보관 후 재검토 주기를 갖는다.

**수락 기준**
*   Given 유언 초안 보관 완료, When 12개월이 경과하면, Then 재검토 알림 Obligation이 발동한다.
*   Given 사용자가 혼인·출생·이혼 등 신상 변동을 입력하면, When 저장하면, Then 즉시 재검토 알림이 생성된다.

## FR-400 · 자산정리 가지 (ESTATE)

### FR-401 · 문서 업로드 & 자동 판독
사용자가 등기부등본·보험증권·통장·증권거래 내역 등을 사진/PDF로 업로드하면 문서에서 텍스트와 구조를 추출한다. (Document Parse + Information Extract — 02.5)

**수락 기준**
*   Given 보험증권 이미지를 업로드하면, When 처리가 끝나면, Then 보험사·증권번호·수익자·보장금액이 항목으로 추출되어 편집 가능한 폼에 채워진다.
*   Given 추출 신뢰도가 낮은 항목, When 표시되면, Then 시각적으로 강조되어 사용자 확인을 유도한다.
*   Given 어떤 문서든, When 업로드하면, Then **주민등록번호·계좌번호는 마스킹되어 저장**된다.

### FR-402 · 자산 인벤토리
추출·수기 입력된 자산을 카테고리별 목록으로 관리한다.
카테고리: 부동산 / 금융 / 보험 / 증권 / 채무 / 물건(유품) / **디지털 자산**

**수락 기준**
*   Given 자산이 3건 이상 등록되면, When 목록을 열면, Then 카테고리별 집계와 함께 표시된다.
*   Given 채무 항목이 존재하면, When 요약을 보면, Then 상속 포기·한정승인 기간(3개월) 안내가 함께 표시된다.

### FR-403 · 디지털 유산 처리 지시
구독 서비스·클라우드·SNS 계정에 대해 **삭제 / 보존 / 특정인에게 이전** 중 하나를 지정한다.

**수락 기준**
*   Given 디지털 계정 등록 시, When 저장하면, Then 처리 방식이 필수 항목이며 비워둘 수 없다.
*   Given 처리 지시가 정리되면, When 문서화하면, Then "디지털 유산 처리 지시서"가 생성되고, `NON_BINDING`으로 판정되어 서명 없이 보관된다.

### FR-404 · 수증자 매핑 & 물건의 이야기
각 자산·물건에 수증자를 연결하고, 물건에는 **왜 그 사람에게 주는지**를 한 문단 남길 수 있다.

**수락 기준**
*   Given 물건에 수증자를 지정할 때, When 저장하면, Then 이유를 적는 칸이 제시된다 (선택 사항, 강제 아님).
*   Given 이유가 작성된 물건, When 수증자에게 전달되면, Then 그 문단이 함께 전달된다.

### FR-405 · 보관·집행 협조 약정 (Custodian · 전자서명 대상)
지정한 Custodian이 인벤토리를 열람·집행에 협조하겠다는 약정을 전자서명으로 체결한다. (Custodian ≠ 유언집행자 — 00.2 §7.1 / 부분 열람 — NFR-713)

**수락 기준**
*   Given Custodian을 지정하면, When 요청을 보내면, Then Custodian에게 모두싸인 서명 요청이 발송되고, 서명 완료 전에는 열람 권한이 부여되지 않는다.

## FR-500 · 전자서명 & 계약 생애주기

> 모두싸인 심사 35점(플로우 15 + 생애주기 12 + 견고성 8)이 전부 이 절에 걸려 있다.

### FR-501 · 서명 요청
게이트를 통과한 문서에 대해 서명 요청을 생성하고 참여자에게 알림이 발송된다.

*   Given `ESIGN_OK` 문서, When 서명 요청을 하면, Then 외부 문서 ID가 반환되고 로컬 상태가 `REQUESTED`가 된다.
*   Given 서명 요청이 실패하면, When 응답을 받으면, Then 로컬 문서는 `DRAFT`를 유지하고 재시도 옵션이 제공된다. **부분 상태로 남지 않는다.**

### FR-502 · 서명 진행 (임베디드)
사용자는 서비스를 벗어나지 않고 서명을 완료할 수 있다.

*   Given 임베디드 서명 URL을 받았을 때, When **2시간이 경과**하면, Then 만료 안내와 함께 **재발급 버튼**이 표시된다. 흰 화면·오류 코드 노출 금지.
*   Given 서명 화면에서, When 사용자가 창을 닫으면, Then 문서는 `REQUESTED`로 유지되고 목록에서 "서명 대기 중"으로 이어서 진행 가능하다.

### FR-503 · 상태 동기화 (웹훅)
외부 서명 이벤트를 수신해 로컬 상태를 갱신한다.

*   Given 동일 이벤트가 **5회 중복 수신**되면, When 처리하면, Then 상태 변경과 부수효과(메일 발송 등)는 **정확히 1회**만 발생한다.
*   Given 웹훅이 문서 ID와 요청자 이메일만 전달할 때, When 처리하면, Then 시스템은 **문서 상세 조회를 추가 호출**해 상태·거절 사유를 보강한다.
*   Given 처리가 10초를 넘길 수 있을 때, When 요청이 오면, Then **즉시 200을 응답하고** 실제 처리는 비동기로 수행한다.

### FR-504 · 리컨실러 (웹훅 유실 대비)
주기적으로 진행 중 문서의 상태를 외부와 대조해 불일치를 교정한다.

*   Given 웹훅이 전혀 도달하지 않은 상태에서 외부 문서가 완료되었을 때, When 리컨실러가 실행되면, Then 로컬 상태가 교정되고 증빙이 확보된다.
*   Given 데모 중, When 관리자 화면을 열면, Then **마지막 동기화 시각과 교정 건수**가 표시된다. ← 견고성 8점 시연 포인트

### FR-505 · 증빙 보관
*   Given 문서가 완료되면, When 증빙을 조회하면, Then 완료 PDF · 서명 시각 · 참여자 · 문서 해시가 함께 제공된다.
*   Given 사용자가 증빙을 다운로드하면, When 검증하면, Then 원본과 동일함을 해시로 확인할 수 있다.

### FR-506 · 거절·중단 처리
*   Given 서명 거절 이벤트, When 수신하면, Then 상태가 `REJECTED`가 되고 **거절 사유**가 저장·표시된다.
*   Given 거절된 문서, When 수정 후 재요청하면, Then 새 문서로 생성되고 이전 이력은 보존된다.

### FR-507 · 리마인드
*   Given 48시간 이상 미서명 문서, When 관리자가 리마인드를 누르면, Then 알림이 재발송되고 발송 이력이 기록된다.

### FR-508 · 이행 관리 (갱신·재검토)
체결 이후의 의무를 스케줄로 관리한다. **여기가 "생애주기 커버리지 12점"의 핵심.**

*   Given 정기후원 약정 체결, When 다음 회차 D-7이 되면, Then 갱신 확인 알림이 생성된다.
*   Given 유언 관련 문서, When 12개월이 경과하면, Then 재검토 알림이 생성된다.
*   Given 갱신 시점에 사용자가 조건 변경을 원하면, When 변경하면, Then **새 약정서가 생성되어 재서명 흐름을 탄다.**

### FR-509 · 게이트 차단 카운터
유효성 게이트가 차단한 문서 생성 시도 횟수를 집계·노출한다. ← AI 품질 기여 5점 시연

*   Given 유언 문서에 대한 서명 시도가 발생하면, When 차단되면, Then 카운터가 증가하고 차단 사유·조문이 로그에 남는다.

# 01.5 · FR — 의사 이력 (Intent Ledger)

**이 페이지는** 체결 이후 **뜻이 바뀌는 과정**을 서명으로 남기는 구조(FR-550)를 다룬다.
핵심은 **FR-554 가족 인지 확인 서명** — 분쟁을 막는 건 문서가 아니라 "몰랐다"의 제거다.
연결된 배점은 생애주기 12 · 서명 플로우 15 · 인간다움 15 · 창의성 20.
주의: 서명 대상 문서명에 **"유언" 단어 금지** — 그 순간 민법 1066조 무효 논란으로 끌려간다.

흐름: `FR-551 의사 확인서` → `FR-552 실질성 등급` → `FR-553 노드 봉인` → `FR-554 가족 인지` → `FR-555 최신성` → `FR-556 유족 열람`
* * *

## FR-550 · 의사 이력 (Intent Ledger)

> FR-104는 "유언에 전자서명할 수 없다"는 제약을 인정했다. 이 절은 그 제약을 **우회하지 않고 뒤집는다.**

유언장의 유효성은 _한 시점_의 문제다. 아무도 풀지 않는 건 _시간에 따른 변화_다. 상속 분쟁에서 실제로 다투는 건 서식이 아니라 셋이다 — **① 당시 의사능력 ② 본인 진의(강요 여부) ③ 이게 마지막 뜻인가.**

서명된 타임스탬프 이력은 유언을 _유효하게_ 만들진 못해도 **믿을 만하게** 만든다.

> **유언장은 순간의 문서다. 사람의 뜻은 과정이다. 우리는 그 과정에 서명한다.**

문서의 단위가 `DocumentDraft` 하나에서 **노드들의 체인**으로 바뀐다.
* * *

## FR-551 · 의사 확인서 (서명 대상의 정의)

서명 대상은 유언이 아니라 **"오늘 시점에 다음 내용이 나의 뜻임을 확인한다"** 는 사실확인 문서.

*   문서명은 **`의사 확인서`** 로 고정. `유언변경서` 등 유언 연상 명칭 **금지** — 그 순간 무효 논란으로 끌려간다.
*   게이트 판정 `ESIGN_OK`. 본문에 유언 전문을 복제하지 않고 **해시 + 항목 요약만**.

**수락** · Given 생성 시 → `ESIGN_OK`이고 유언 전문 미포함 / 제목에 "유언" 미포함

## FR-552 · 변경의 실질성 등급 (서명 인플레이션 방지)

잦은 재서명 요구는 **그 자체가 마찰**이고(P4·NFR-708), 감정적으로 무거운 주제에서 특히 해롭다. 모든 변경에 서명을 요구하면 사용자는 변경 자체를 회피하게 된다 — 그러면 이력의 존재 이유가 사라진다.

| 등급 | 내용 | 처리 |
| ---| ---| --- |
| MATERIAL | 수증자·배분비율·기부처·기부액·Custodian | 재서명 |
| MINOR | 문구 다듬기, 오탈자, 연락처 | 버전만 증가 |
| ANNOTATION | 마음의 편지 추가 | 이력 append |

**수락** · 문구 수정 → 재서명 요구 없음 / 수증자 변경 → MATERIAL 판정 / 한 세션 2번째 서명 필요 시 **다음 세션으로 연기 제안**

## FR-553 · 원장 노드 봉인

**이게 없으면 이력은 역효과를 낸다.** 불만 있는 상속인이 "5번 바꿨다 = 판단력 없었다"로 공격할 수 있다. 각 노드가 **그 시점의 정황**을 함께 봉인하면 이력은 오히려 능력의 증거로 뒤집힌다.

노드에 봉인되는 것:
*   변경 전후 요약 + **변경 사유(본인 진술)**
*   서명 시각 · 서명자 · 서명 수단
*   **선택 정황 기록** — 입회인, 작성 환경 메모 등 (있는 경우에만)
*   직전 노드 해시 → **해시 체인**

**일반 사용자의 능력 정황은 별도 임상 기록이 아니라 시스템이 이미 가진 것들이 담당한다** — 대화 원문(조리 있는 발화 자체가 정황), 세션의 규칙성, 본인이 남긴 변경 사유. 임상적 컨디션 기록·의료진 입회는 **확산 단계(기관·말기 도입)의 강화 요건**이지 기본 요건이 아니다. 스키마의 `condition_note` · `witness` 필드는 그래서 선택(optional)이다.

**수락** · 임의 노드 1바이트 수정 → 이후 전체 불일치 표시 / 정황 기록 없이 생성된 노드도 유효

## FR-554 · 가족 인지 확인 서명 (다자·다단계) ★

**가장 강한 버전은 혼자 재서명하는 게 아니다.** 변경 시점마다 가족이 **"뜻이 바뀌었고 나는 알았다"** 에 함께 서명한다. 분쟁을 막는 건 문서가 아니라 **"몰랐다"의 제거**다.

*   가족 서명은 **동의가 아니라 인지**. 동의로 읽히면 유류분 포기 오해가 생긴다.
*   본인이 통지 대상을 지정하고, **통지하지 않을 자유도 보장**한다 (P4).

**수락** · MATERIAL 확정 시 본인→가족 순 다자 요청 / 가족은 변경 내용과 **본인의 변경 사유**를 함께 열람 / 가족 거부해도 본인 확인서 효력 유지, 거부 사실만 기록

## FR-555 · 최신성 판정

전후 유언이 저촉되면 뒤엣것이 우선한다. **"어느 게 최신인가"가 그 자체로 소송거리다.**

**수락** · 유효 노드가 **단 하나로 특정**되고 나머지 `SUPERSEDED` / 철회 시 `REVOKED`, 원본 물리 삭제 없음

## FR-556 · 유족 열람 뷰

Custodian·유족이 원장을 **시간순 타임라인**으로 열람. 각 시점의 사유·서명자·(있다면) 정황 기록 + **해시 검증 결과**. 열람은 `audit_logs`에 기록.

# FR-110 · 중심 축 — 마음 유언 (세션 주기 무관 관리 · 가지 분기)

**이 페이지는** 서비스의 등뼈를 정의한다. 트랙 선택은 없다. 하나의 대화가 있고, 법적 서류는 거기서 갈라져 나온다.
**서비스는 장기가 아니다 — 세션의 주기가 길 수 있을 뿐이다.** 저장·관리가 되므로 간격이 아무리 벌어져도 유지된다 (00 헌법 §3.1).
기존 FR-301(회상 인터뷰)은 이 축의 **엔진**으로 승격되며, 질문 세트·수락 기준은 그대로 유효하다.
* * *

## FR-110 · 단일 진입 · 세션 주기 무관 관리

트랙 선택 화면이 없다. 진입은 한 문장이다 — **"무엇을 남기고 싶으세요?"**

*   첫 발화가 **명시적 가지 의사**이면 축을 거치지 않고 바로 가지로 진입한다 (→ FR-115 직접 진입)
*   그 외에는 회상 인터뷰로 시작한다. 1화면 1질문, 언제든 "오늘은 여기까지"
*   중단한 세션은 **간격이 얼마나 벌어져도** — 하루 뒤든 6개월 뒤든 — 정확히 그 지점부터 재개된다. 짧게 써도 완전하고, 길게 써도 관리된다
*   재개 시 이전 이야기의 짧은 요약을 먼저 보여준다 ("지난번엔 어머니 이야기를 하셨어요")
*   질문 세트는 FR-301의 5축 20문항 + 존엄요법 9문항 프로토콜을 참조하되, 순서 이탈을 허용한다

**수락 기준**
*   Given 신규 사용자가 진입하면, When 첫 화면이 뜨면, Then 트랙·카테고리 선택 UI가 **존재하지 않는다.**
*   Given 3개월 전 중단한 세션이 있을 때, When 재접속하면, Then 이전 요약과 함께 그 지점부터 이어진다. (= 주기 무관 성질의 대표 테스트)

> **『맥락』** 이전 구조의 트랙 선택은 헌법 1장(마찰이 결심을 죽인다)과 충돌했다. 그리고 "장기 서비스"라는 표현도 버렸다 — **장기는 서비스의 속성이 아니라 사용 패턴의 허용 범위다.** 세션 간격이 10분이든 6개월이든 시스템 동작은 같다. 이 프레임이 세 가지를 동시에 푼다: 7분 데모도 완전한 사용이 되고(시간 압축은 결함 은폐가 아니라 성질의 증명), express 1회 사용자(P3)가 예외가 아니게 되고, 짧은 주기 사용자(말기 단계 확산)도 같은 시스템으로 수용된다.

## FR-111 · 축적과 문서화 — 살아있는 유서

세션이 끝날 때마다 시스템은 이야기를 **마음 유언 문서**에 반영할 것을 제안한다.

*   AI는 편집 **초안**만 만든다. 반영 여부·문안은 사용자가 확정한다 (P1)
*   원문 발화는 절대 덮어쓰지 않는다. 문서의 모든 문단은 근거 발화(`source_utterance`)를 참조한다
*   AI가 다듬은 문장과 사용자가 직접 쓴 문장은 시각적으로 구분된다 (FR-303과 동일 규칙)
*   문서는 버전을 갖는다. 갱신마다 새 버전, 이전 버전 보존

**수락 기준**
*   Given 세션 종료 시, When 문서 반영을 제안하면, Then 사용자가 거절해도 세션 기록은 보존되고 문서만 갱신되지 않는다.
*   Given 문서의 어떤 문단이든, When 근거를 조회하면, Then 원본 발화와 세션·시각이 표시된다.

## FR-112 · 저장·관리 — 보존과 전달

*   마음 유언과 세션 원본(텍스트·음성)은 **삭제하지 않고 보존**한다 (보안 정책은 01.7)
*   문서 상단에 "법적 효력이 없는 문서입니다" 고지 영구 포함 (`NON_BINDING`)
*   수신인·전달 시점 지정: `즉시` / `지정일` / `사후`. 본인은 언제든 회수 가능 (P4)
*   원하는 시점에 **스냅샷**을 봉인할 수 있다 — 해시 + 시각 기록, 의사 이력(FR-550) 노드로 연결

**수락 기준**
*   Given 전달 시점이 '사후'인 문서, When 지정일 이전에 수신인이 접근하면, Then 차단되고 접근 시도가 기록된다.
*   Given 스냅샷 봉인 뒤, When 1바이트 수정한 사본을 검증하면, Then 불일치가 표시된다.

> **『맥락』** "저장·관리가 되니 길게 끌고 가도 된다"는 명제의 구현체다. 보존·전달·회수·봉인이 있으므로 세션이 언제 끊겨도 아무것도 사라지지 않는다.

## FR-113 · 이어쓰기 관리 — 리듬 유지

*   마지막 세션에서 일정 기간이 지나면 **이어쓰기 초대**를 보낸다 (독촉이 아니라 초대. 긴급성 문구 금지 — NFR-708)
*   신상 변동(혼인·출생·이혼 등) 입력 시 즉시 이어쓰기 제안 (FR-305와 동일 트리거)
*   "그만 알림받기" 선택 시 존중하고 기록한다. Obligation 스케줄러(FR-508) 인프라 공용

**수락 기준**
*   Given 이어쓰기 초대 발송 시, When 문구를 검사하면, Then "지금", "빨리", "놓치기 전에" 류의 긴급성 표현이 없다.

## FR-115 · 가지 감지·제안·승인 + 직접 진입

대화에서 법적 서류로 이어질 수 있는 신호를 감지하면, AI는 **제안**한다. 가지를 여는 것은 사용자다.

### A. 감지·제안 (기본 경로)

*   모든 제안에는 근거 발화가 붙는다. 근거 없는 제안은 생성 자체가 금지된다
*   제안 문구는 확인형이다 — "방금 ○○ 재단 이야기를 하셨어요. 후원 약정을 정리해볼까요?" (권유·설득 금지)
*   사용자가 닫은 가지는 **다시 제안하지 않는다** (거부 이력 영구 보존)
*   가지 무게 등급:

| 등급 | 가지 | 처리 |
| ---| ---| --- |
| 가벼움 | DONATION\_NOW, HERITAGE\_SUPPORT | 즉시 진행 가능 |
| 중간 | ESTATE | 즉시 진행 가능, Custodian 지정은 별도 확인 |
| 무거움 | LEGACY\_GIFT, HANDWRITTEN\_WILL | 제안 → 다음 세션에 재확인 → 진행. 같은 세션 내 체결 금지 |

### B. 직접 진입 — Express Lane

**축은 기본 경로이되 유일한 경로가 아니다.** 이미 결심하고 온 사람에게 회상 인터뷰를 요구하는 것 자체가 마찰이다 (헌법 1장). 과제②의 기부 흐름(약정→답례품→동의→서명)은 이 경로로 곧장 시연된다.

*   사용자의 발화가 특정 가지에 대한 **명시적 의사**이면 — 대상 + 행위 의지가 한 발화에 드러나면 ("부산에 기부하고 싶어요", "유언장을 준비하러 왔어요") — 감지·제안 단계를 **건너뛰고** 해당 가지로 바로 진입한다
*   애매한 발화("뭔가 남기고 싶어요", "정리를 좀 하고 싶은데")는 직접 진입이 아니다 → 축으로 시작한다
*   `branch_proposals.origin` 에 `DETECTED` / `EXPRESS` 를 기록한다 (분석·감사용)
*   **무거운 가지의 직접 진입**: "다음 세션 재확인"은 적용하지 않는다 — 그 규칙의 방어 대상은 _AI가 감정적 순간에 밀어넣는 것_이지 _본인이 스스로 시작하는 것_이 아니다. 대신 진입 직후 **숙려 화면**을 1회 거친다: 유류분 등 필수 고지 + "오늘 진행할게요 / 다음에 할게요" 선택. 재촉 문구 금지
*   직접 진입으로 가지를 마친 사용자에게는 종료 화면에서 축(마음 유언)을 **한 번만** 소개한다. 거절하면 다시 권하지 않는다

**수락 기준**
*   Given 첫 발화가 "부산에 기부하고 싶어요"일 때, When 응답하면, Then 회상 인터뷰 질문 없이 기부 슬롯 수집이 시작되고 origin=EXPRESS 가 기록된다.
*   Given 첫 발화가 "유언장을 준비하고 싶어요"일 때, When 진입하면, Then 즉시 진입하되 숙려 화면(고지 + 오늘/다음에 선택)이 표시되고 재촉 문구가 없다.
*   Given 발화가 "뭔가 남기고 싶어요"처럼 애매할 때, When 판정하면, Then 직접 진입이 아니라 축이 시작된다.
*   Given 사용자가 감정적으로 무거운 발화 중 AI가 감지한 제안(DETECTED)일 때, When 무거운 가지면, Then 그 세션에서 체결 단계로 진행할 수 없다. (기존 규칙 유지)

> **『맥락』** 축 중심 구조가 과제②의 데모 동선을 길게 만든다는 비판에 대한 답이다. 직접 진입이 있으면 특별상 심사자는 기부 흐름을 30초 만에 보고, 인간다움 심사자는 축의 서사를 본다. 두 채점표를 한 구조로 만족시키는 장치이며, "명시적 의사는 존중한다"는 P1의 자연스러운 귀결이다. 기간 무관 관리 프레임에서 express 1회 사용자는 예외가 아니라 **세션 1회짜리 정상 사용자**다.

# NFR-710 · 보안 & 데이터 관리

**이 페이지는** 원본 보존 결정에 따른 보안 요구와, 에이전트가 지켜야 할 보안 지침을 정의한다.
결정: **원본(대화 텍스트·음성, 업로드 이미지)은 삭제하지 않고 보존한다.** 보존하기로 했으므로 보호 의무가 그만큼 커진다.
* * *

## NFR-710 · 원본 보존 정책

*   보존 대상: 세션 대화 원문(텍스트·음성), 업로드 원본 이미지·PDF, 마음 유언 전 버전
*   저장: 비공개 버킷 + **저장 시 암호화(at rest).** 공개 URL 발급 금지
*   접근: **서명된 임시 URL(만료 15분)** 로만. URL은 화면·로그에 출력하지 않는다
*   삭제: 시스템은 자동 삭제하지 않는다. 삭제는 **본인의 명시적 요청**으로만 하며, 삭제 요청도 감사 로그에 남는다 (P4)
*   열람: 열람권 매트릭스(본인 / 지정 수신인 / Custodian)를 통과한 주체만. 모든 열람은 `audit_logs`에 기록

**수락 기준**
*   Given 발급된 서명 URL, When 15분이 지나면, Then 접근이 거부된다.
*   Given 어떤 원본 파일이든, When 로그·에러 메시지를 검사하면, Then 파일 경로·서명 URL이 존재하지 않는다.

## NFR-711 · 외부 전송 고지

*   업로드 원본은 판독을 위해 **외부 API(Upstage Document Parse)로 전송**된다. 이 사실을 업로드 화면에 **전송 전에** 고지한다
*   고지 문구 예: "올려주신 문서는 내용 추출을 위해 AI 분석 서버로 전송됩니다."
*   대화 내용도 Solar LLM으로 전송되므로 최초 세션 시작 시 1회 고지한다
*   전송 전 클라이언트에서 주민등록번호 패턴이 감지되면 경고를 표시한다 ("주민등록번호가 보입니다. 가린 뒤 올리시는 것을 권장합니다")

**수락 기준**
*   Given 첫 업로드 시도, When 파일 선택 직후, Then 외부 전송 고지가 전송보다 먼저 표시되고 동의 없이는 전송되지 않는다.

> **『맥락』** 등기부등본·통장 사진이 외부 서버로 나간다는 사실이 이전 문서 어디에도 없었다. 대회 시연에서는 문제없지만 Q&A에서 나오면 답이 없는 지점이었다. 먼저 고지하고, 발표에서 "실서비스라면 온프레미스 OCR 또는 전송 전 마스킹이 필요하다"고 선제적으로 말한다.

## NFR-712 · 마스킹의 전 경로 적용

*   식별번호(주민등록번호·계좌·카드) 마스킹은 OCR 추출 경로뿐 아니라 **수기 입력 폴백 경로에도 동일하게** 적용된다
*   식별번호 입력 필드는 저장 시점에 `1234-56******` 형태로 변환되며, 원문은 어디에도 저장되지 않는다
*   테스트 픽스처·시드 데이터에도 실존 가능한 식별번호를 넣지 않는다 (전량 가상 패턴)

**수락 기준**
*   Given 수기 입력 폼에 계좌번호를 타이핑했을 때, When 저장 후 DB를 조회하면, Then 원문이 아닌 마스킹 값만 존재한다.

## NFR-713 · Custodian 부분 열람

*   Custodian 열람권은 전부/전무가 아니라 **카테고리 단위**로 부여한다 (부동산만 / 금융 제외 등)
*   기본값은 최소 권한. 본인이 명시적으로 범위를 넓힌다
*   열람 범위는 협조 약정서 본문에 명시되고, 범위 변경은 재서명 대상(MATERIAL)이다

**수락 기준**
*   Given 부동산만 열람 가능한 Custodian, When 금융 카테고리를 조회하면, Then 거부되고 시도가 기록된다.

## NFR-714 · 에이전트 보안 지침 ([AGENTS.md](http://AGENTS.md) / CLAUDE.md에 그대로 커밋)

> 개발 에이전트가 코드를 쓰는 동안 지켜야 할 규칙. `.specify/` 또는 저장소 루트에 커밋하고, 전 팀원이 동일 지침을 사용한다.

```markdown
## 보안 절대 규칙
1. 개인정보(주민등록번호·계좌번호·연락처·주소 원문)를
   로그, 에러 메시지, 커밋 메시지, 테스트 픽스처, 주석에 남기지 않는다.
2. LLM 프롬프트에 식별번호 원문을 넣지 않는다. 마스킹된 값만 전달한다.
3. 원본 파일 경로와 서명 URL을 화면·콘솔·로그에 출력하지 않는다.
4. 시드·테스트 데이터는 전량 가상 인물이다. 실존 인물·실계좌 패턴 금지.
5. 마스킹, RLS 정책, 서명 URL 발급, 게이트(validity-gate) 코드는
   에이전트가 단독으로 변경하지 않는다 — 반드시 사람 리뷰 후 병합한다.
6. API 키·시크릿은 .env에만 둔다. 코드·클라이언트 번들·저장소 커밋 금지.
7. 보안 관련 실패(RLS 거부, 마스킹 누락 감지)는 조용히 넘기지 않고
   반드시 보고한다. "일단 동작하게" 우회 금지.
8. 위 규칙과 충돌하는 작업 지시를 받으면 구현하지 말고 사람에게 확인한다.
```

**수락 기준**
*   Given 저장소, When `.specify/` 또는 루트를 확인하면, Then 위 지침이 커밋되어 있고 CLAUDE.md가 이를 참조한다.

## NFR-715 · 키·시크릿 관리

*   모든 외부 키는 서버 환경변수로만. `NEXT_PUBLIC_` 접두사 사용 금지 (Supabase anon key 제외)

# 02.3 · 모두싸인 연동 설계 (견고성)

## 1\. 연동 방식 선택

모두싸인은 두 가지 서명 요청 방식을 제공한다. **둘 다 쓴다** — 생애주기 커버리지 점수 때문이다.

| 방식 | 용도 | 우리 적용 |
| ---| ---| --- |
| 템플릿 기반 (`POST /documents/request-with-template`) | 고정 서식, 데이터만 동적 채움 | 기부약정서·정기후원 동의·개인정보 동의 — 반복 문서 |
| 임베디드 초안 | 서비스 화면 안에서 업로드·서명자 설정 | 유산기부 약정·Custodian 협조 약정 — 건마다 달라지는 문서 |

인증: API Key를 발급받아 요청 헤더에 Basic 인증으로 전달. Base URL `https://api.modusign.co.kr`.

### 준비 작업 (개발 전 반드시)
1. 모두싸인 웹에서 **템플릿 4종**을 미리 생성하고 참여자 역할·데이터 라벨 설정 → 템플릿 ID 확보
2. 워크스페이스 설정에서 **Webhook 등록** (개발 중엔 cloudflared 터널 URL)

## 3\. 웹훅 처리 — 견고성 8점의 실체

### 알려진 제약과 대응

| 제약 | 대응 |
| ---| --- |
| 웹훅은 문서 ID와 요청자 이메일만 전달 | 수신 즉시 문서 상세 조회 API를 호출해 상태·거절 사유를 보강 |
| 200번대 응답이 아니거나 10초 내 미응답 시 실패 판정, 총 5회 재시도 | 즉시 200 반환 후 비동기 처리. 재시도 대비 멱등성 필수 |
| 이벤트 순서 보장 없음 | 상태 머신 허용 전이 표로 역행 방지 (`SIGNED` → `REQUESTED` 무시) |
| 웹훅 유실 가능 | 폴링 리컨실러로 보정 |
| 임베디드 URL 2시간 만료 | 만료 시각 저장 → UI에서 재발급 버튼 |

### 처리 흐름 (아웃박스 패턴)

```
POST /api/webhooks/modusign
  1. 서명/시크릿 검증
  2. external_event_id로 webhook_events INSERT
     → 중복이면 ON CONFLICT DO NOTHING (멱등성)
  3. 즉시 200 응답            ← 10초 제한 회피
  ────────────────────────────
  비동기 워커 (또는 다음 요청 시 드레인)
  4. 미처리 이벤트 조회
  5. getDocument(documentId) 호출 → 상태·거절사유 보강
  6. 상태 머신 전이 시도 (허용되지 않으면 스킵 + 로그)
  7. 완료 시: PDF 다운로드 → Storage 저장 → sha256 → evidences
  8. Obligation 생성 (정기후원·유언 재검토)
  9. processed_at 기록, audit_logs 기록
```

**부수효과(메일 발송·Obligation 생성)는** **`processed_at IS NULL`** **조건 안에서만 실행한다.** 이것이 FR-503 "정확히 1회" 수락 기준의 구현.
* * *

## 4\. 리컨실러 (FR-504)

```
GET /api/cron/reconcile   — 5분 주기
  1. status = REQUESTED 이고 last_synced_at < now - 5min 인 문서 조회
  2. 각각 getDocument() 호출
  3. 외부 상태 != 내부 상태 → 상태 머신 전이 + 교정 카운터++
  4. last_synced_at 갱신
```

관리자 화면에 **"마지막 동기화 · 교정 건수"** 를 노출한다. 심사위원 앞에서 웹훅을 일부러 끊고 리컨실러가 상태를 맞추는 걸 보여주면 견고성 8점은 사실상 확보된다.

### 2.1 ⚖️ 결정 지점 (ADR-7 후보) — 검증 호출의 모델

사전교육 3-3은 "최상위 난도에선 프론티어와 격차가 있으니 역할을 나누라"고 했고, 대회 규정은 타사 병행 자유 + **Upstage 활용 시 가점**(독점 요건 아님)이다. 즉 어느 쪽이든 감점은 없다. 선택지는 셋:

|  | A. Solar 단독 | B. 고정 하이브리드 | C. 측정 기반 스위치 (권고) |
| ---| ---| ---| --- |
| 구성 | 전 런타임 solar-pro3 (검증은 reasoning effort=high) | 검증·편집초안만 프론티어 고정, 나머지 solar | 기본 A. 검증 1지점만 ModelPort 뒤에 두고 env로 전환 가능 |
| 품질 상한 | 모순 탐지에서 격차 가능성 | 최고 | 측정 결과에 따름 |
| 운영 복잡도 | 키 1개, mock 1벌 | 키 2개, mock 2벌, 장애 지점 2배 | A와 동일 + 어댑터 30분 |
| 발표 서사 | "빼면 무너진다" 순도 최대 | 사전교육 소개 전략 인용 | "직접 측정해 결정했다" — 사전교육 2-10 "직접 써보고 판단" 그대로 실행 |
| 리스크 | 검증 누락률이 높으면 게이트 신뢰 하락 | 데모 중 외부 의존 2배 | 측정 픽스처 준비 비용 |

**결정 절차 (Day 1, T002 직후)**: 수락 기준에서 뽑은 검증 픽스처 10케이스(금액 누락, 수증자 모순, 기간 역전 등)를 solar-pro3 reasoning=high로 실행 → 통과율 기록 → **팀이 임계(예: 9/10)를 정해 미달 시에만 해당 1지점을 프론티어로 전환.** 결과와 근거를 ADR-7로 커밋. 어느 쪽이든 게이트·계산은 코드이므로 모델 격차가 법적 정확성을 흔들지는 않는다 — 검증은 마지막 그물이지 1차 방어가 아니다.

**개발 단계는 별개**: Claude Code를 개발 오케스트레이터로 쓰는 것은 런타임 선택과 무관하며 이미 확정 ([AGENTS.md](http://AGENTS.md) 체계).

**단순함의 원칙 (주최 경고)** — "해커톤 최다 자멸 원인은 과설계". 우리 파이프라인은 어느 옵션에서도 에이전트가 아니라 **워크플로 조합**(Prompt Chaining + Routing)이다. 발표에서 이 용어로 설명한다.

## 3\. Embeddings 신규 사용처 — 세션 회상 검색

**왜 핵심 경로인가**: 축의 세션 간격은 며칠에서 몇 달까지 벌어질 수 있다 — **기간 무관 관리(헌법 §3.1)를 실제로 성립시키는 장치**가 이것이다. 간격이 벌어질수록 재개 시 "지난번엔 어머니 이야기를 하셨어요"(FR-110)와 마음 유언 문단의 근거 발화 연결(FR-111)은 최근 N개 요약으로 불가능해지고, 수백 발화에 대한 **의미 검색**이 필요해진다. 6개월 만에 돌아온 사람에게 어제 온 사람과 같은 연속성을 주는 것 — 그게 이 기능의 정의다.

| 시점 | 동작 |
| ---| --- |
| 발화 저장 시 | embedding-passage 배치 적재 → utterance\_embeddings (pgvector) |
| 세션 재개 시 | 마지막 요약 + 관련 과거 발화 top-k (embedding-query) → 재개 카드 |
| 대화 중 | 과거 인물·사건 재언급 시 관련 발화를 Solar 컨텍스트에 주입 |
| 마음 유언 편집 시 | 문단 초안 ↔ 근거 발화 연결 후보 검색 |

"이 API를 빼면 무너지는가" 정직한 답: Solar·DP·IE는 **무너진다.** Embeddings는 간격이 긴 사용에서 연속성이 **크게 약화된다** (최근 요약 폴백 가능). 발표에서도 이 수위로.

## 4\. reasoning\_effort 운용

| 호출 | effort |
| ---| --- |
| 축 대화 | minimal (NFR-702) |
| 구조화·가지 감지 | minimal + JSON 강제 |
| 렌더링 전 검증 | high |

## 5\. 비용 가드 ⚠️

사전교육 명시: **크레딧 소진 후에도 API는 멈추지 않고 결제수단으로 과금.**
Usage 하루 2회 당번 · UPSTAGE\_MODE=mock 즉시 전환 유지 · 데모 응답 사전 캐싱 · 임베딩은 세션 종료 배치 · 쿠폰은 Billing > Credit > Redeem code (이월 불가).

## 6\. 02.2(v1)에서 달라진 점

2. Embeddings 신규 채택 — **기간 무관 관리의 기술적 성립 조건**

# 03.0 · MVP 절단 계획 — 기능 나열과 명세 연결

> 옛 Phase 구조(03.1~03.4)를 대체하는 기준. **절단 단위는 기능 묶음이 아니라 "증명 가능한 명제"다.**  
> 각 MVP는 한 문장의 명제를 증명하고, 그 명제가 심사 배점과 1:1로 연결된다. 뒤에서부터 버린다 — M0·M1은 사수.

## 절단 원칙

1. **수직으로 자른다.** 화면만·백엔드만 완성된 층은 MVP가 아니다. 각 층은 진입→체결→보관까지 관통한다.
2. 모든 기능은 FR/NFR ID를 갖는다. **ID 없는 기능은 만들지 않는다** (01.4 추적성 규칙).
3. M0의 파이프라인 코드(구조화→게이트→문서→서명→보관)는 이후 모든 층이 **재사용**한다. 층이 올라가도 파이프라인은 하나다.

## M0 · "말이 서명이 된다" — 최소 관통 절단
